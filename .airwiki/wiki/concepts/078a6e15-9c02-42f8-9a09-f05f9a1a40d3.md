# Alcance y coherencia de estados en la UI

Los indicadores resumidos deben describir el mismo ámbito que la pantalla a la que conducen y reutilizar la misma derivación de estado. Un estado nunca debe aparecer como fallido si la vista de destino muestra el mismo subsistema como listo sin explicar ese fallo.

## Separación de ámbitos

- **General / Conocimiento local** resume la preparación de la IA local: instalación en curso, modelo seleccionado listo, reinicio requerido, configuración pendiente o incidencias del modelo.
- La salud, indexación o reconciliación de una Wiki pertenece a la biblioteca y a la propia Wiki. Sus fallos se muestran allí con contexto y una acción de recuperación; no convierten `General` en fallido.
- El indicador global y la navegación de Settings reutilizan el mismo view model que el encabezado del panel de destino.

## Progreso asíncrono

- El progreso debe permanecer visible junto al objeto o control que inició la operación. Deshabilitar controles o cambiar el cursor a ocupado no constituye feedback suficiente.
- Cuando no existe un porcentaje real, se muestra un indicador indeterminado acompañado por un verbo específico, por ejemplo “Comprobando…”, “Conectando…” o “Actualizando integración…”. No se fabrica precisión.
- El contenido previo que siga siendo seguro y útil permanece visible durante la operación. Solo se bloquean las acciones incompatibles.
- El estado activo identifica la operación y su ámbito para que una acción sobre una app no haga parecer ocupadas a todas las tarjetas. Inicio, finalización y fallo se exponen de forma visible y con semántica de estado sin robar el foco.

## Criterio de IA local lista

El modelo seleccionado está listo cuando el runtime está activo, el modelo recomendado coincide con el activo, está instalado y su licencia fue aceptada. Si el recomendado coincide con el modelo pendiente, el estado indica que hace falta reiniciar. Una instalación en curso usa estado de trabajo y los issues del modelo usan atención.

## Recuperación de la primera búsqueda

El onboarding puede terminar sin preparar el modelo local, pero nunca debe dejar la acción principal sin explicación ni salida visible. Mientras la búsqueda no esté lista:

- el paso de preparación mantiene un enlace visible hacia el estado/configuración de IA local;
- el campo de búsqueda muestra una acción visible para consultar ese estado, además de cualquier explicación accesible;
- hardware incompatible, preparación diferida, progreso y fallo se distinguen como estados tipados;
- cancelar o posponer no se presenta como éxito de búsqueda ni obliga a desactivar protecciones del sistema.

Esta regla está implementada desde `main` en `d119515423de66a41dc6de165b2670d2fa4b316b` y queda cubierta por pruebas de componentes, E2E y baselines visuales.

## Atajos contextuales y menús nativos

Los atajos globales de Biblioteca, Búsqueda y Configuración permanecen en el WebView para poder respetar el contexto de edición:

- `Cmd/Ctrl+1`, `Cmd/Ctrl+K` y `Cmd/Ctrl+,` se bloquean únicamente cuando el origen efectivo está editando texto: input textual, textarea, contenteditable o roles textbox/searchbox, considerando composed path y elemento activo.
- Los mismos atajos siguen disponibles sobre checkbox, switch, select y controles no textuales.
- `Escape` cierra diálogos, modales y la confirmación inline del actualizador.
- Los menús nativos no duplican esos aceleradores contextuales. Biblioteca, Búsqueda y Configuración invocan los flujos existentes; Nueva Wiki usa el acelerador global convencional.
- macOS expone AirWiki, File, Edit, View y Window; Windows expone File, Edit, View y Window, con Close/Exit. Edit y cierre usan semántica nativa y un apagado ordenado.
- Las etiquetas del menú siguen el locale guardado. La QA del candidato instalado en macOS y Windows sigue siendo un gate de release.

Estas reglas están implementadas en `main` por `00faaa533ef9a791755d4899429a878509e0753d` y `91dac4657b8d859b28c3b285ca7f8dbe66f09fe4`.
