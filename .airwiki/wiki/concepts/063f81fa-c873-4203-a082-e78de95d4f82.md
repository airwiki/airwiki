# Firma de releases y actualizaciones estables

## Vigencia e historial

La elección de SSL.com descrita abajo es histórica. El [ADR 0016](https://github.com/airwiki/airwiki/blob/19f70fc/docs/adr/0016-signpath-foundation-windows-signing.md) sustituyó únicamente el proveedor de firma Windows por SignPath Foundation, condicionado a aceptación, configuración protegida y aprobación independiente. Los requisitos operativos de SSL.com que aparecen al final también corresponden a esa etapa histórica. Permanecen vigentes el transporte por GitHub Releases y la verificación criptográfica del updater.

El [ADR 0017](https://github.com/airwiki/airwiki/blob/f8337c8/docs/adr/0017-platform-split-release-candidate.md) define por separado un candidato macOS firmado y notarizado con beta técnica Windows sin firma, sin canal updater ni promoción a Latest. La autoridad actual son esos ADRs y el proceso de release versionado.

## Decisión histórica de ADR 0015

- Los releases estables de Windows usan SSL.com eSigner con un certificado OV, sujeto a prevalidación de la entidad. La clave de firma permanece no exportable en el HSM del proveedor.
- El job protegido verifica CKA y CodeSignTool, escanea el conjunto exacto de binarios AirWiki antes de firmar, selecciona el certificado mediante su huella SHA-256 y verifica Authenticode, timestamp y payload antes de publicar.
- El updater tiene un único canal estable alojado en GitHub Releases: `latest.json` referencia assets con firmas Tauri separadas. GitHub y sus redirects son transporte no confiable, no autoridad criptográfica.
- El cliente solo acepta una versión estrictamente mayor con firma Tauri válida y exige confirmación humana. Windows vuelve a comprobar Authenticode sobre el MSI descargado; macOS y Windows pasan verificación nativa durante preparación y promoción.
- Los prereleases técnicos no entran al updater. La ruta histórica SignPath/NSIS fue retirada.

## Ensayo protegido de macOS

- `macos-notarization-rehearsal.yml` permite ensayar Developer ID, Hardened Runtime, notarización, stapling y verificación nativa sin crear tags, GitHub Releases, `latest.json` ni publicaciones.
- El dispatch vincula una confirmación al SHA completo y solo acepta el tip exacto, limpio y verde de `main`. Revalida los checks requeridos antes de exponer secretos y nuevamente antes de registrar el resultado.
- La ejecución usa el environment protegido `macos-signing`, limitado a `main`, con revisión obligatoria y autoaprobación bloqueada. Los permisos del workflow son de solo lectura.
- El paso de prevalidación inmediatamente anterior a la firma no recibe secretos. Las credenciales se materializan en un keychain y directorio efímeros que se eliminan al terminar.
- El workflow no conserva binarios; solo retiene por tiempo acotado un recibo JSON saneado con hashes. Ese recibo no sustituye la prueba instalada de Gatekeeper ni la validación de actualización N→N+1.

## Implementación versionada

La migración de firma y updater quedó integrada mediante [61b19beec242fb22b83804a3ee02262506ed215f](https://github.com/airwiki/airwiki/commit/61b19beec242fb22b83804a3ee02262506ed215f). El ensayo protegido de macOS quedó integrado mediante [2180e2f1fa9eecd108029e8f2d1ff162c1797af2](https://github.com/airwiki/airwiki/commit/2180e2f1fa9eecd108029e8f2d1ff162c1797af2).

## Estado operativo

El código y sus controles están implementados, pero todavía no existe un release estable firmado. Siguen siendo obligatorios el onboarding comercial y la validación de entidad de SSL.com, el certificado y credenciales protegidas, la confirmación escrita del transporte de secretos antes de habilitar `AIRWIKI_ESIGNER_SECRET_TRANSPORT_APPROVED`, la custodia recuperable de la clave Tauri, un ensayo protegido exitoso de macOS seguido por una prueba instalada de Gatekeeper, y una prueba instalada N→N+1 con recuperación en Windows y macOS.
