# ADR 0011: Store portable project memory in `.airwiki`

- Status: Accepted
- Date: 2026-08-23
- Supersedes in part: ADR 0002 (project-selection workflow) and ADR 0010
  (AI memory only in private managed storage)

## Context

AirWiki's application memory is durable and open OKF, but its private vault
cannot travel with a code project, study folder, or cloned repository. Agents
therefore need manual Wiki selection on every machine and collaborators cannot
receive the same project documentation with the project itself. Putting SQLite,
capabilities, indexes, embeddings or grants in a repository would instead leak
local state and make clone identity and authorization ambiguous.

Project memory must remain explicit. Merely opening an arbitrary folder must not
create files, grant an application, or cause private content to leave the
device. Git conflicts and external edits must fail closed rather than letting an
old SQLite projection disclose content that no longer matches the visible OKF
bundle.

## Decision

AirWiki supports two `ai_memory` scopes. `personal` memory remains in the
private vault. `project` memory uses exactly one portable Wiki per folder with
this version-one layout:

```text
.airwiki/
├── project.yaml
└── wiki/
    ├── index.md
    └── concepts/
        └── <uuid>.md
```

`project.yaml` is strict YAML containing `schema_version: 1`, portable
`project_id`, portable `wiki_id`, and `name`. `index.md` declares OKF v0.2 and
is not regenerated by agent writes. New concept filenames are UUIDs. Only the
manifest and visible OKF bundle live in `.airwiki`; every operational artifact
remains in AirWiki's private application state.

Each canonical local root gets an independent SQLite `collection_id`, even when
several clones share the portable IDs. Migration 0016 marks existing AI memory
as `personal` and adds attachments and expiring confirmation requests. An
attachment records canonical root, portable identity, manifest fingerprint and
one of `active`, `invalid`, `missing`, or `identity_conflict`. Scope/origin
triggers reject incompatible state.

Initialization is explicit and uses a sibling staging directory plus atomic
rename. MCP `initialize_airwiki_project` and first
`open_airwiki_project` create only a deduplicated ten-minute request. They never
write files or grant access. Native approval repeats root, filesystem,
manifest, fingerprint and application checks, then creates or attaches the
bundle and grants that application `editor`. Approval is local to the
application/root/portable-identity combination; another clone requires another
approval.

Project bundle mutations share the managed-bundle lock, fingerprint contract,
atomic replacement and journal used by personal memory. The lock is never held
across an async suspension. Project updates preserve unknown OKF fields,
provenance and verification, do not regenerate `index.md`, and do not consume
the personal-vault total quota. Existing concept, bundle and mutation-rate
limits remain.

Startup and filesystem events reconcile attachments before MCP or network
disclosure. Reconciliation marks the attachment unavailable and clears its
projection before validating. Missing, invalid or identity-conflicting bundles
retain their files and a sanitized diagnostic but cannot be read, searched,
written, shared over LAN, published, or sent to external AI. Recovery restores
the projection only after the exact visible bundle validates again. AirWiki
does not resolve Git conflicts or regenerate project memory through the repair
executor.

`search_airwiki_memory` is application-scoped local lexical search. It accepts
at most 2 KiB, returns at most twenty stable non-deprecated concepts, bounds
snippets to 1 KiB, and requires the same live grant and active attachment as
`list`, `get`, `write`, and `deprecate`. Revocation cuts all of those paths
immediately. LAN, public and external-AI disclosure remain separate opt-in
confirmations and also require an active attachment.

“Delete” for project memory means detach: withdraw grants and network state,
remove local projections and attachment state, and preserve `.airwiki`
unchanged. AirWiki never invokes Git.

## Consequences

- Project documentation is open, reviewable in ordinary diffs, and portable
  across supported agents without a vendor-specific memory service.
- A clone can reuse portable identity without reusing local authorization or
  operational state.
- External edits and conflicts can temporarily make memory unavailable; this is
  an intentional fail-closed boundary.
- Static `index.md` reduces merge conflicts at the cost of not listing every
  concept link automatically.
- Personal memory remains private and is neither copied nor migrated into
  projects.
- V1 supports one default project Wiki per folder. Git automation, conflict
  resolution, personal-to-project import and implicit initialization remain out
  of scope.

## Rejected alternatives

- **Keep all memory only in the private vault:** prevents portable project
  knowledge and clone onboarding.
- **Store SQLite or capabilities in `.airwiki`:** leaks device state and couples
  portable identity to one installation.
- **Authorize by portable ID alone:** lets an unapproved clone inherit another
  root's authority.
- **Create `.airwiki` when a folder opens:** causes surprising repository writes
  and bypasses explicit intent.
- **Regenerate `index.md` on every concept write:** creates a shared Git conflict
  hotspot.
- **Have AirWiki stage, commit or resolve conflicts:** crosses the user's source
  control authority and obscures ordinary review.
- **Silently trust the last valid projection:** can disclose content after the
  visible bundle becomes missing, invalid or conflicted.
